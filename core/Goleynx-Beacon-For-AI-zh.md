# Goleynx 信标事件体系规格说明

本文档是 Goleynx 多智能体信标事件体系的完整规格。结构面向机器解析。每一条陈述均可对照参考实现验证。

---

## 1. 信标语法

### 1.1 四段式结构

每条信标由最多四个正交段组成。段之间以连字符分隔。

```
{窗口}{轮次}[-限定符[-目标]]
```

| 段位 | 位置 | 类型 | 取值范围 | 必填 |
|------|------|------|----------|------|
| 窗口段 | 1 | 大写字母 | A, B, C, D, E, F | 是 |
| 轮次段 | 2 | 4位补零整数 | 0001–9999 | 是 |
| 限定符段 | 3（首条 `-` 之后） | 小写字母+数字 | -d0X, -sXXXX-XX, -vXX-XX, -rXX-XX, -rcXX-XX, -acXX | 有连字符时必填 |
| 目标段 | 4（末段） | 大写字母 | -D, -E, -F, -G, -H | 仅定向广播 |

### 1.2 大小写规则

- 窗口标识：始终大写（A, B, C, D, E, F）
- 限定符/动作标记：始终小写（d, s, v, r, rc, ac）
- 控制词：始终小写（off, stp）

### 1.3 信标类型（共12类）

| 窗口 | 格式 | 含义 | 示例 | 正则模式 |
|------|------|------|------|----------|
| A | `A{轮次}` | 轮次触发（用户提交） | A0001 | `^A\d{4}$` |
| B | `B{轮次}` | 中枢结论（目标已提炼） | B0001 | `^B\d{4}$` |
| C | `C{轮次}` | 审查结论（架构已定） | C0001 | `^C\d{4}$` |
| B/C | `{B|C}{轮次}-d0X` | 蓝图交付（D01-D06） | B0001-d01 | `^[BC]\d{4}-d0[1-6]$` |
| B/C | `{B|C}{轮次}-s{组}-00` | 调度触发（唤醒 e10） | B0001-s0001-00 | `^[BC]\d{4}-s\d{4}-00$` |
| B | `B{轮次}-s{组}-{版次}-{窗}` | 工单下发 | B0001-s0001-01-D | `^B\d{4}-s\d{4}-\d{2}-[DEF]$` |
| D/E/F | `{窗}{轮次}-v{版次}-{迭代}` | 送审请求 | D0001-v01-01 | `^[DEF]\d{4}-v\d{2}-\d{2}$` |
| C | `C{轮次}-r{版次}-{迭代}-{窗}` | 定向驳回 | C0001-r01-01-D | `^C\d{4}-r\d{2}-\d{2}-[DEF]$` |
| D/E/F | `{窗}{轮次}-rc{版次}-{迭代}` | 历史纠查送审 | D0001-rc01-01 | `^[DEF]\d{4}-rc\d{2}-\d{2}$` |
| C | `C{轮次}-rc{版次}-{迭代}-{窗}` | 纠查驳回 | C0001-rc01-01-D | `^C\d{4}-rc\d{2}-\d{2}-[DEF]$` |
| C | `C{轮次}-ac{序号}-{窗}` | 督导意见 | C0001-ac01-D | `^C\d{4}-ac\d{2}-[DEF]$` |
| C | `C{轮次}-00` | 架构重生通知（架构已变→通知 E05 重建步骤） | C0001-00 | `^C\d{4}-00$` |
| B | `B{轮次}-00` | 步骤重生完成握手（E05 完成→通知 E08/E09 发 off） | B0001-00 | `^B\d{4}-00$` |
| — | `off{轮次}` | 正常结束 | off0001 | `^off\d{4}$` |
| — | `stp{轮次}` | 强制终止 | stp0001 | `^stp\d{4}$` |

### 1.4 限定符参考

| 限定符 | 含义 | 产生方 |
|--------|------|--------|
| -d01 | goals.md 已更新 | e01 (B), e07 (C, 修正) |
| -d02 | requirements.md 已更新 | e02 (C) |
| -d03 | architecture.md 已更新 | e03 (C) |
| -d05 | steps.md 及步骤文件已更新 | e05 (B) |
| -d06 | summary.md 已更新 | e06 (B) |
| -sXXXX-00 | 调度触发（非工单下发） | e05 (B) 或 e07 (C) |
| -sXXXX-VV-W | 发给执行窗 W 的工单 | e10 (B) |
| -vVV-II | 送审，版次 VV，迭代 II | 执行窗 (D/E/F) |
| -rVV-II-W | 驳回，版次 VV，迭代 II，给窗 W | e08 (C) |
| -rcVV-II | 纠查送审 | 执行窗 (D/E/F) |
| -rcVV-II-W | 纠查驳回，给窗 W | e09 (C) |
| -acSS-W | 督导意见，序号 SS，给窗 W | e08 督导 (C) |
| -00 | 架构重生握手（C0001-00=通知E05重建步骤，B0001-00=E05完成通知） | E08/E09 (C) / e05 (B) |

## 2. 窗口与轮次系统

### 2.1 窗口标识

| 窗口 | 编号 | 名称 | 角色 |
|------|------|------|------|
| A | 101 | 对话窗 | 接收用户输入；发出 A{轮次} |
| B | 201 | 中枢窗 | 目标提炼、步骤拆解、调度派发 |
| C | 301 | 督导窗 | 审查、督导、任务槽收敛、架构体检 |
| D | 401 | 执行窗 | 按工单产出交付物；可扩容 D→E→F… |
| E | — | 执行窗 | 横向扩展 |
| F | — | 执行窗 | 横向扩展 |

### 2.2 轮次系统

- 轮次为 4 位补零整数：0001–9999
- 收到 `off` 或 `stp` 后轮次 +1
- `off`：正常结束（所有执行窗审查通过）
- `stp`：强制终止（用户操作或迭代熔断）
- off 和 stp 触发后轮次统一 +1

## 3. 引擎系统

### 3.1 引擎自注册

窗口代理（window-agent.ts）在启动时和每轮步进后扫描 `engines/` 目录。对每个 trigger.pattern 非空的 .json 文件，在事件总线上注册监听器。匹配的信标触发 runEngine()。

### 3.2 引擎注册表（9个引擎）

| 引擎 | 触发正则 | 运行方 | 产出 | 行为 |
|------|----------|--------|------|------|
| e01 | `^A\d{4}$` | B(201) | D01 goals.md | 从对话中提炼目标 |
| e02 | null（链式） | C(301) | D02 requirements.md | 需求清单；e07 通过 chain_engine 调起 |
| e03 | null（链式） | C(301) | D03 architecture.md | 架构树+scaffold；e02 链式调起 |
| e04 | — | — | D04 review-rules.md | 缺号：D04 由 project.ts 模板静态产出 |
| e05 | `^C\d{4}(?:-00)?$` | B(201) | D05 steps.md + 步骤拆分 | 步骤拆解：正常触发=发 B{轮}-s{轮}-00 调度；REGEN 模式（-00 触发）=只重生步骤+发 B{轮}-00 握手，不调度 |
| e06 | `^off\d{4}$` | B(201) | D06 summary.md | 终点引擎；写轮次总结；不发信标 |
| e07 | `^B\d{4}$` | C(301) | 交叉验证 | 分流枢纽：CHANGED=false→发 C{轮}-s{轮}-00；CHANGED=true→chain e02 |
| e08 | `^[A-Z]\d{4}-v\d{2}-\d{2}$` | C(301) | 审查结论+驳回指令 | 五维审查；max_iterations=6；四路出口：off/chain e09/r/ac |
| e09 | `^[A-Z]\d{4}-rc\d{2}-\d{2}$` | C(301) | 纠查结论 | 双模式（init/reconcile）；漂移检测→分区派单→复核→架构同步 |
| e10 | `^[BC]\d{4}-s\d{4}-00$` | B(201) | 调度工单 | 容量决策（CAP=10）+ LLM分区 + 工单生成 + validate_dispatch + broadcast_all |

### 3.3 引擎动作类型（14类）

read_file, write_file, llm_call, parse, broadcast, chain_engine, user_confirm, scaffold, foreach_executor, split_steps, resolve_steps, prepare_dispatch, apply_partition, broadcast_all

## 4. 信标流转

### 4.1 第一轮（完整序列，14步）

```
步骤  信标                 发出方     接收方      动作                    产出
1     A0001               对话窗     e01(201)    目标提炼                 core/goals.md
2     B0001-d01           e01        面板         目标交付通知              D01 显示
3     B0001               e01        e07(301)    交叉验证                 判定 CHANGED
4     (chain e02)         e07        e02(301)    需求清单                 core/requirements.md
5     (chain e03)         e02        e03(301)    架构树+scaffold          core/architecture.md
6     C0001-d03           e03        面板         架构交付通知              D03 显示
7     C0001               e03        e05(201)    步骤拆解                 core/steps.md + 拆分 JSON
8     B0001-d05           e05        面板         步骤交付通知              D05 显示
9     B0001-s0001-00      e05        e10(201)    调度触发                  —
10    B0001-s0001-01-D    e10        401(D)      工单下发                  dispatch/B{信标}.json
11    D0001-v01-01        401(D)     e08(301)    送审                     workspace/ 文件
12    C0001-r01-01-D(*)   e08        401(D)      驳回                     reject/C{信标}.json
13    C0001-ac01-D(*)     e08督导    401(D)      督导意见                  advisory/C{信标}.json
14    off0001             e08        全局         轮次结束                  summary.md; 轮次+1
```

`(*)` 表示条件步骤（仅当审查不通过或督导介入时发生）。

### 4.2 第二轮+ 分支A — 目标未变（CHANGED=false）

```
步骤  信标                 发出方     接收方      动作
1     A0002               对话窗     e01(201)    目标提炼（判未变）
2     B0002-d01           e01        面板         追加"目标未变化"
3     B0002               e01        e07(301)    交叉验证 → CHANGED=false
4     C0002-s0002-00      e07        e10(201)    直通调度触发（跳过 e02/e03/e05）
5     B0002-s0002-01-D    e10        401(D)      工单（沿用已有步骤文件）
6     D0002-v01-01        401(D)     e08(301)    送审
7     off0002             e08        全局         轮次结束
```

### 4.3 第二轮+ 分支B — 目标已变（CHANGED=true）

```
步骤  信标                 发出方     接收方      动作
1     A0002               对话窗     e01(201)    目标提炼（判已变）
2     B0002-d01           e01        面板         追加新目标
3     B0002               e01        e07(301)    交叉验证 → CHANGED=true
4     (chain e02)         e07        e02(301)    全量重建：需求清单
5     (chain e03)         e02        e03(301)    全量重建：架构树
6     C0002               e03        e05(201)    全量重建：步骤拆解
7     B0002-s0002-00      e05        e10(201)    调度触发（新步骤）
8     B0002-s0002-01-D    e10        401(D)      工单下发
9     D0002-v01-01        401(D)     e08(301)    送审
10    (chain e09)         e08        e09(301)    历史纠查·init
11    C0002-rc01-01-D     e09        401(D)      纠查工单
12    D0002-rc01-01       401(D)     e09(301)    纠查送审
13    off0002             e09        全局         轮次结束（架构一致性核对后）
```

### 4.4 架构变化后的步骤重生

当 E08 架构合并或 E09 架构同步完成后，架构树已更新但开发步骤仍是旧树的版本。此时 E08/E09 通过 C{轮次}-00 信标通知 E05 重建步骤。

```
步骤  信标                 发出方     接收方      动作
1     C0001-00            E08/E09    e05(201)    通知架构已变，触发步骤重生
2     (e05 REGEN 模式)     e05        201内部      读 runtime/arch-files.json → LLM 重新生成全部开发步骤
3     B0001-00            e05        E08/E09     通知步骤重建完成
4     off0001             督导中枢    全局         发 off（B{round}-00 handler 验证 regen 标记已清除后触发）
```

E05 在 REGEN 模式下：
- 读 `runtime/arch-regen.json` 判定触发源（E08 或 E09）
- 追加 D05 steps.md（`## d05 第 X 轮 开发步骤微调`）
- 删除 `d{轮次}/` 下旧步骤文件 → 重新拆分写入全部组 JSON
- 清除 `runtime/arch-regen.json`
- 广播 `B{轮次}-00`（而非 `B{轮次}-s{轮次}-00`）

## 5. 审查与督导

### 5.1 审查循环

- 执行窗通过 `{窗}{轮次}-v{版次}-{迭代}` 送审
- e08 执行五维审查：指令完成度、架构合规、规则合规（7条+D04审查规则）、量化红线（文件≥400行打回、函数≥80行打回、嵌套≥4层警告）、整体结论
- 通过 → 检查收敛 → ALL_PASSED 且 TARGET_CHANGED=false → 发 off
- 通过 → 检查收敛 → ALL_PASSED 且 架构已变化（E08 合并或 E09 同步后）→ 写 runtime/arch-regen.json + 发 C{round}-00 → E05 重生步骤 → B{round}-00 → 督导中枢验证后发 off
- 通过 → 检查收敛 → ALL_PASSED 且 TARGET_CHANGED=true 且 HISTORICAL_DONE≠true → chain e09
- 不通过 → 写入驳回指令到 `reject/C{轮次}-r{版次}-{迭代}-{窗}.json` → 广播 `C{轮次}-r{版次}-{迭代}-{窗}`

### 5.2 熔断机制（max_iterations=6）

当某窗送审迭代达到 6（如 D0001-v01-06）且审查仍未通过：
- 窗口代理写入 melted 标记到终端
- 不发出驳回信标
- 督导看护检测到 melted → 换窗或放弃该槽
- 全部槽 abandoned → 发 `stp{轮次}`

### 5.3 督导层（任务槽+看护器）

督导层（e08 的一部分）维护任务槽账本追踪每个执行窗：
- `pending` → 窗已收到工单，尚未送审
- `delivered` → 窗已通过审查
- `abandoned` → 窗不可恢复失败

看护器每 5 秒运行一次：
- 槽超过 60 秒无活动 → 检查终端状态
- melted → 立即换窗
- 瞬态失败（timeout/parse/empty）→ diagnose 最多 2 次 → 换窗
- 空工单 → 直接 abandon

督导意见信标：`C{轮次}-ac{序号}-{窗}`，kind=diagnose（原窗重跑）或 reassign（换窗接手）。

### 5.4 三层兜底验证

| 层 | 触发条件 | 负责方 | 动作 |
|----|----------|--------|------|
| 1 | 正常轮次收敛 | e08 收敛点 | 覆盖制架构体检：磁盘代码 vs 架构树 → 不符则覆盖 |
| 2 | 目标变化轮次 | e09 架构同步 | 重建后一致性核对：workspace 文件 vs 架构树 → 追加同步段 |
| 3 | 调度下发前 | e10 validate_dispatch | 广播前闸门：扫工单路径对照架构树 → 剥离私建层 |

## 6. 调度与执行

### 6.1 容量决策（CAP=10）

每个执行窗单次最多处理 10 个文件。

```
TARGET = min(已开窗数, max(1, ceil(文件总数 / 10)))
```

### 6.2 分区分配

- LLM 执行智能分区：将文件清单完整、无重复地分配给 TARGET 个窗
- apply_partition 做校验：全覆盖、零重复、窗数正确
- 校验失败 → 回退确定性取模切片

### 6.3 下发前交叉验证网关（validate_dispatch）

e10 生成 dispatch/ 工单后、broadcast_all 发信标前：
1. 读架构树（D03）抽取合法顶层目录
2. 扫描每张工单的 workspace/ 路径
3. 若顶层不在架构树中但第二层是合法根 → 剥离私建层
4. 修正工单 instruction + 同步修正终端和面板
5. 全部验证通过 → broadcast_all 并发发出全部调度信标

### 6.4 文件映射

信标字符串等于 dispatch/reject/advisory 目录中的文件名：

| 信标 | 文件路径 |
|------|----------|
| B0001-s0001-01-D | dispatch/B0001-s0001-01-D.json |
| C0001-r01-01-D | reject/C0001-r01-01-D.json |
| C0001-ac01-D | advisory/C0001-ac01-D.json |

### 6.5 执行窗的三种工作模式

| 模式 | 触发信标 | 行为 |
|------|----------|------|
| 首次执行 | `B{轮}-s{组}-{版}-{窗}` | 读调度工单 → LLM 产出全部文件 → 写入 workspace/ → 发 v 送审 |
| 驳回重写 | `C{轮}-r{版}-{迭}-{窗}` | 读驳回文件 → LLM 按审查意见逐条修正 → 写入 → 送审迭代+1 |
| 纠查修正 | `C{轮}-rc{版}-{迭}-{窗}` | 读纠查工单 → LLM 按新架构修正历史文件 → 写结果摘要 → 发 rc 送审 |

## 7. 状态机与规格边界

### 7.1 运行状态机

| 状态 | 含义 | 提交按钮 | 终止按钮 |
|------|------|----------|----------|
| IDLE | 空闲 | 可点（启动第一轮） | 灰 |
| RUNNING | A{N} 执行中 | 灰（防重复） | 可点（发 stp） |
| QUEUED | A{N+1} 排队中 | 灰 | 灰 |
| STOPPED | A{N} 已中止 | 可点（重跑当前轮） | 灰 |

### 7.2 非对称断代

| 窗口 | 断代时机 | 效果 |
|------|----------|------|
| A (101) | 发出或截获 A{轮次} 时 | 此后输入归为下一轮（提前断代） |
| B/C/D (201/301/401) | 截获 off{轮次} 或 stp{轮次} 时 | 轮次结束后资产才归为下一轮（延后断代） |

### 7.3 规格边界

本规格覆盖的内容：
- 信标语法、编码规则和正则模式
- 窗口标识和轮次系统
- 引擎触发模式和自注册机制
- 所有轮次场景的完整信标流转
- 审查、督导、调度和执行规则
- 状态机及断代规则

本规格不覆盖的内容：
- 实现语言、框架或运行时
- 信标=文件名映射原则之外的文件系统布局
- LLM prompt 内容（system_prompt 和 user_prompt_template 为实现细节）
- UI 渲染、面板布局或视觉设计
- 网络传输或跨进程通信（参考实现使用进程内事件总线）

### 6.6 真正的并发调度（未来）

当前实现：每一轮调度一组步骤，S 编号与轮次对齐（0001→S0001, 0002→S0002）。
信标体系天然支持同一轮次内并发调度多组步骤——B{轮次} 前缀保持不变，
不同执行窗领取不同步骤编号，同时并行推进。

轮次与步骤是两个独立维度：
  · 轮次（B0001）由中枢窗的轮次管理器决定——收到 off 才递增。
  · 步骤（S0001）由 e05 拆解产生，是任务分组编号。
  · 两者互不绑定。

并发示例——第 1 轮调度三个窗各拿一个步骤：
  B0001-S0001-01-D  （窗D拿第1组任务）
  B0001-S0002-01-E  （窗E拿第2组任务）
  B0001-S0003-01-F  （窗F拿第3组任务）

进度标记：一轮结束时必须持久化当前进度——记录最后一个已完成步骤。
标记文件：runtime/progress.json → {"lastStep": "S0003"}。
下一轮（B0002）启动时，e10 读该标记，从 S0004 开始调度：
  B0002-S0004-01-D, B0002-S0005-01-E, B0002-S0006-01-F

约束：
  · 步骤编号（S0001-S9999）是全局递增序列，由 e05 首次拆解产生后永不变化。
  · 目标变化时 e05 重新拆解，产生新序列，旧进度标记作废，从头开始。
